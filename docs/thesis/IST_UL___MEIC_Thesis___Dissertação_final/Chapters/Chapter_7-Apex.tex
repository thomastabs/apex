\fancychapter{Implementation}
\label{chap:apex}

The framework presented in \Cref{chap:proposal} describes a methodology. This chapter presents Apex, the working software system instantiating it, which serves both as evidence that the framework's governance constructs are implementable and as the vehicle through which the framework is demonstrated and evaluated in \Cref{chap:demonstration,chap:evaluation}. In \ac{DSRM} terms the two are distinct artefacts produced by the same Design and Development activity: a method and its instantiation. The chapter addresses the realisation dimension of the problem defined in \Cref{chap:problem}, and doing so honestly means reporting which constructs resisted implementation as well as which did not.

\section{Purpose and Positioning}
\label{sec:apex_purpose}

% The distinction below is the one that most needs stating early and plainly:
% Apex is not competing with coding agents on convenience.

Apex is not a coding agent and is not positioned against one. A coding agent accelerates the writing of code; Apex governs whether the code that results still answers the question that prompted it. The two are complementary, and the distinction is the whole reason the system exists because acceleration without anchoring is the condition \Cref{chap:intro} shows moves the bottleneck to review rather than removing it. Every artefact Apex produces carries a stable specification identifier back to the requirement it derives from, so divergence between what was agreed and what was built becomes a detectable event rather than a drift nobody is positioned to notice.

\begin{figure}[htb]
    \centering
    \includegraphics[width=\linewidth]{./Images/demo-apex-phase1-review-draft.png}
    \caption[Apex's interface, Phase 1 Review Draft]{Apex's interface at Phase 1's Review Draft step: AI-drafted Gherkin scenarios for two stories awaiting Trio approval, and the right-hand Active Context panel showing the project's versioned specification files (\Cref{sec:spec_anchored}).}
    \label{fig:apex_ui}
\end{figure}

What Apex deliberately does not do is as much part of its definition. It does not train or fine-tune models, and treats the model as a third-party capability that may change beneath it. It does not provision infrastructure: where a release needs configuration or migration scripts it generates them for a human or a \ac{CI} pipeline to execute, and never applies them itself. And it does not replace the project management tool a team already uses. It sits above that tool, reads and writes through it, and expects the team's existing board to remain the system of record for work items, which is why the framework's board guidance in \Cref{sec:work_organisation} asks only that a team's own columns map onto framework phases rather than that they be renamed.

\section{Architecture}
\label{sec:apex_architecture}

Apex is a split full-stack application. The frontend uses Next.js 15 with TypeScript, while the backend uses Python 3.12 with FastAPI, connected through a typed REST API. React Query manages server state and Zustand client state. Backend routers remain thin, with workflow logic isolated in a service layer and schemas defining request and response boundaries. \Cref{fig:apex_architecture,fig:apex_architecture_b} show the overall arrangement. Five architectural properties directly realise framework constructs:

    \label{fig:apex_architecture}
\end{figure}

\begin{figure}[!htb]
    \centering
    % Avoid a dedicated float page ("p"), which can produce a mostly-empty page.
    \includegraphics[width=\linewidth,height=0.43\textheight,keepaspectratio]{./Images/architecture-b.png}
    \caption[Apex architecture, part two]{Apex architecture, part two: guarded egress layer, external integrations and the browser-direct version-control exception.}
    \label{fig:apex_architecture_b}
\end{figure}

\begin{itemize}[leftmargin=0.6cm, itemsep=0.4em]

\item \textbf{Spec-anchored storage.} Workflow state is stored in per-tenant, per-project specification files rather than an application database. A single storage service abstracts local and cloud backends while enforcing project isolation, making Spec-Anchored Continuity concrete.

\item \textbf{Repository and design grounding.} Two additional context files extend the project-management data. \texttt{github-context.md} is generated by shallow-cloning and repacking the connected repository with \texttt{repomix}, grounding Phase~2--6 generation in the actual implementation and refreshing automatically after repository pushes. \texttt{figma-context.md} provides equivalent grounding for connected Figma files through the guarded proxy and can render a linked frame as an image, allowing developer packs to reference the designed screen directly.

\item \textbf{Single-writer concurrency.} Shared file state was initially protected by process-local locks, requiring a single replica. An optional coordination layer now provides cross-replica locking while preserving the same behaviour when disabled.

\item \textbf{Proxy-first external integration.} User-configurable outbound requests pass through a guarded server-side proxy that validates destinations and limits responses, reducing \ac{SSRF} risk. The browser-direct integration is the documented exception and keeps its credential outside the backend.

\item \textbf{Project-management adapter.} Apex integrates with existing boards through one adapter interface. Taiga was the original and received the bulk of the implementation effort; Plane was completed behind the same interface, while the Jira adapter was started but left incomplete once it became clear Taiga and Plane were the priority targets. Tool-independence holds at the operation level, although provider-specific \ac{API} limitations still constrain the guarantees Apex can offer.

\item \textbf{Provider abstraction.} Model requests are routed through a provider-independent boundary, with vendor-specific failures mapped to common typed exceptions so the rest of the system does not branch on provider. Three providers are supported today, selected from the model identifier alone: Anthropic, OpenAI and Google.

\end{itemize}

The framework defines Spec-Anchored Continuity as a two-layer structure by lifetime but leaves file granularity open, meaning it is not a one-to-one translation. Apex implements this through a fixed set of cumulative global and project-local Markdown documents, an implementation choice rather than a framework requirement. Three additional Apex-specific artefacts extend that structure. The \textbf{developer pack} is a per-task implementation brief generated from the locked Gherkin, technical specification, design bundle and related task packs; saving it marks the task \texttt{pack\_ready}. The \textbf{test plan} is the \ac{QA} hat's per-story \ac{BDD} script set, while the \textbf{deploy pack} records the infrastructure-delta verdict for Deployment. All three are revisable Markdown artefacts that can be exported individually or project-wide for use outside Apex.

\item \textbf{AI Defect Escape Rate.} The construct remains observable only through a proxy: reported, linked, post-deployment defects. The system cannot directly identify every production defect or reliably attribute it to generated logic, so the metric is deliberately retained as a weaker but still useful operationalisation rather than presented as full implementation.

\item \textbf{Spec-drift detection.} Implementation exposed an unstated assumption that specifications must be scoped per story for drift to be attributable. The technical specification does not satisfy that assumption, so detection was removed there, while the story-scoped functional specification allowed a later partial revival. \section{The Governance Analytics Surface}
\label{sec:apex_analytics}

% Mechanism-level companion to the mapping table above. This describes the
% instrument, not evaluation results.

\Cref{tab:apex_mapping} establishes which governance constructs are realised; this section describes how the corresponding measures are produced. Apex computes all governance analytics on demand in a single backend service using the story index and context files already generated by the workflow. At project scale, this requires no caching. The measures are therefore derived from operational state rather than practitioner or model self-report, and most require no separate instrumentation step. The surface exposes six figures:

\begin{itemize}[leftmargin=0.6cm, itemsep=0.45em]

\item \textbf{Context Traceability Rate.} The proportion of deployed stories whose context chain remains complete. Apex verifies the required artefacts, confirms the story in the deployment log, and rejects stories with unresolved backward-trace flags, unacknowledged conformance regressions, or incomplete verification records. The metric deliberately does not claim item-level ownership within the technical specification, since that relationship is not represented by the system.

\item \textbf{Bolt Cycle Time.} Computed per task from the earliest \texttt{pack\_ready} timestamp to the earliest \texttt{done} timestamp and reported as median and 90th percentile in hours. Story-level gate-transition time is retained separately so queueing and review are not confused with the task-level quantity defined by the framework.

\item \textbf{Spec Conformance Rate.} The mean Phase~6 conformance score, from 0 to 100, across eligible stories with a saved conformance report. Stories that were never checked are excluded from the mean; coverage is therefore displayed separately as checked versus eligible stories.

\item \textbf{Fix-Bolts.} Counts corrective micro-cycles raised before deployment, reported as a total, the number of affected stories, and the mean per story. Because these defects are caught by quality assurance, a higher count represents detected pre-deployment correction rather than escaped failure.

\item \textbf{AI Defect Escape Rate.} The proportion of deployed stories linked to at least one confirmed post-deployment bug recorded after deployment. This remains a proxy: unreported or unlinked defects are invisible, and Apex cannot determine whether a defect originated specifically from generated code.

\item \textbf{Stories Tracked.} The total number of indexed stories, together with the deployed subset. This provides the denominator needed to interpret the other proportions and aggregates.

\end{itemize}

The measures differ in the provenance of their inputs. Bolt Cycle Time, Context Traceability Rate, Spec Conformance Rate and Stories Tracked derive entirely from state Apex writes while the workflow executes. Fix-Bolts and AI Defect Escape Rate additionally depend on issue data from the connected project-management tool, which Apex can read but cannot guarantee to be complete. Their interpretation therefore carries stronger caveats. The analytics surface is treated here only as an instrument; its readings on the evaluated project are reported in \Cref{chap:evaluation}.

\section{Design History and Practitioner Feedback}
\label{sec:apex_history}

% Formative evaluation feeding back into design, not a changelog.

Feedback gathered during the construction of Apex informed both the framework and the tool. To make the \ac{DSRM} iteration explicit, the changes below are reported as observations and resulting design responses rather than as a release history. Reverted changes are included because they also reveal where assumptions failed in practice. Two changes affected the framework itself:

\begin{itemize}[leftmargin=0.6cm, itemsep=0.4em]

\item \textbf{Removal of a dedicated DevOps role.} An external DevOps Alliance originally held deployment approval and infrastructure-security responsibilities. Practitioner feedback showed that a role defined mainly by supervision is unlikely to be staffed consistently, so those responsibilities were reassigned to the person performing deployment. The resulting framework rationale is discussed in \Cref{sec:roles}.

\item \textbf{Removal of mandatory dual sign-off in Phase~2.} Design locking originally required separate approval from design and technical leads. In smaller teams this either blocked progress or reduced the gate to duplicate approval by the same person. The gate was therefore redefined around recorded evidence rather than role-specific signatures, as reflected in \Cref{tab:gates}.

\end{itemize}

\noindent Three further changes affected the Apex implementation:

\begin{itemize}[leftmargin=0.6cm, itemsep=0.4em]

\item \textbf{Design-conflict detection.} File overlap within an epic generated false positives, so detection was narrowed and ultimately removed when it proved insufficiently reliable.

\item \textbf{Spec-drift detection.} Project-wide technical specifications caused changes to cascade across unrelated stories, one real edit flagging 44 stories at once. The detector was removed at that granularity while its audit trail was retained, leading to the partial implementation described in \Cref{sec:apex_framework_mapping}.

\item \textbf{Authentication for a design integration.} An authentication flow requiring an operator-registered application and backend-held secret was reverted because it conflicted with Apex's zero-configuration deployment model.

\end{itemize}

The formative feedback came from five practitioners consulted individually during construction, with one consulted again after substantial revision. The sessions were informal: there was no interview guide, fixed question set, recording or demographic collection. Feedback was captured in contemporaneous author notes and linked to the resulting changes. This record is therefore suitable for showing that the design changed in response to use, but not for estimating the prevalence or strength of practitioner opinion.

Three of those practitioners later participated separately in the semi-structured interviews reported in \Cref{sec:interviews}. The two evidence sources serve different purposes: this section documents formative design change, whereas the interviews provide a structured account of practitioner views using a written guide and consistent thematic analysis.

The second consultation round produced the most consequential reframing. Feedback challenged the work to distinguish the framework from a general-purpose coding agent, justify it against explicit alternatives, state its relationship to existing models more precisely, and present Apex as an instantiation of the method rather than as the primary contribution. Those points are reflected in \Cref{sec:apex_purpose}, \Cref{sec:alternatives}, \Cref{sec:phases} and \Cref{chap:demonstration}, making the revision traceable across the final dissertation.

A later sixth consultation with an Agile/Scrum expert is treated separately in \Cref{sec:interviews}. It evaluated the demonstration argument rather than shaping the framework during construction and produced no direct change to either the framework or Apex.

\section{Quality Assurance of the Implementation}
\label{sec:apex_qa}

% Proportionate. This establishes the demonstration platform is sound; it is
% not the contribution.

This section establishes that the platform the demonstration in \Cref{chap:demonstration} runs on is sound; it is not itself a research contribution, and the detail below is kept proportionate to that purpose.

Testing is layered by what each layer can catch: at the time of writing the backend carries roughly 1,638 tests, the frontend roughly 318 unit tests, and there are 24 end-to-end test cases across 12 specifications, a snapshot of a codebase that continues to change.

Testing also surfaced defects with methodological significance. A section-parsing routine truncated a live project's technical specification part-way through because it anchored on headings the model itself also emits. An automation step once marked a story's quality gate as passed with no verification behind it, and the deployment step trusted that result rather than checking it. And the identity anchor determining which tenant a request belongs to, along with an integrated tool's listing endpoint, each leaked across project boundaries before being corrected. A coverage badge reported the model's own claim about which scenarios it had covered, at face value; it is now reconciled server-side against the parsed specification, and a claimed scenario that does not match a real one is dropped rather than displayed.

\section{Limitations of the Implementation}
\label{sec:apex_limitations}

The limitations of Apex as a system must be separated from the limitations of the framework as a methodology, because conflating them would let a defect in one be read as a refutation of the other.

\vspace{0.2cm}

\noindent\textbf{System-level limitations:}

\begin{itemize}[leftmargin=0.6cm, itemsep=0.4em]

\item The single-writer fallback path, which most deployments would run, is a real ceiling rather than a theoretical one (\Cref{sec:apex_architecture}).

\item Apex observes only what passes through it: it can see a story's specification chain, and, once a defect is reported through the project-management tool and linked to a story, a proxy signal that a deployment shipped a fault, but it cannot observe a defect never reported there, or attribute one to generated logic specifically.

\end{itemize}

\noindent\textbf{Framework-level limitations exposed through implementation:}

\begin{itemize}[leftmargin=0.6cm, itemsep=0.4em]

\item \textbf{AI Defect Escape Rate, at the observation point the framework's own definition presumes, is not instantiable by this class of system}: nothing in the framework says who owns production telemetry for generated logic specifically, and a tool sitting above a project-management board has no access to it regardless of who does; what is instantiable is the weaker proxy described in \Cref{sec:apex_framework_mapping}.

\item \textbf{Spec-drift detection presumes a granularity the framework does not state}, namely a per-story rather than a per-project specification, and the instantiation revealed the omission by failing on it; it now holds for the functional specification and remains open for the technical one.

\end{itemize}

Both framework-level limitations remain open even after the September 2026 work reported above and are carried into \Cref{chap:evaluation} as findings rather than as defects to be excused. The two proxies differ in kind, and \Cref{tab:apex_mapping} names both as proxies rather than presenting either as the construct itself: Bolt Cycle Time was one briefly and by accident, while AI Defect Escape Rate is one by design from the outset. A substitution left unnamed is indistinguishable from the thing it substitutes for.
